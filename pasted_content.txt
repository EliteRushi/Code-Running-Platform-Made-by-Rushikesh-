Project Name: Browser-Based Code Playground
1. Project Overview
Build a simple, modern, responsive website that functions as an online code editor and code execution environment.

The website should allow users to write, edit, execute, and test code directly in their browser without installing any software.

The interface should be inspired by the W3Schools Tryit Editor and Python editor:

Reference: https://www.w3schools.com/python/trypython.asp?filename=demo_helloworld

The website must support the following programming languages and file types:
- HTML (.html)
- CSS (.css)
- JavaScript (.js)
- Python (.py)
Users should be able to create multiple files, connect them to each other, and execute their code.

The website must have two primary pages:

Page 1: Code Editor

Users write, edit, manage, and run their code.

Page 2: Output Viewer

Displays the result of the code execution, such as a rendered webpage or program output.

The entire project must be deployable on GitHub Pages.
2. Technical Requirements
Use only the following technologies for the main application:
- HTML5
- CSS3
- Vanilla JavaScript
For Python execution, use a browser-compatible Python runtime such as Pyodide.

Do not use:
- A backend server.
- A database.
- PHP or Node.js servers.
- User account systems.
- Cloud storage.
- Server-side code execution.
The application should work as a static website hosted on GitHub Pages.

External libraries may be loaded from public CDNs when necessary.

For example, Pyodide may be loaded from its official CDN to execute Python code in the browser.

Important: The first Python execution may require an internet connection to download the Python runtime. Once loaded, Python execution can work offline if the required runtime files are cached and the browser permits their use.

The editor should not transmit the user's code to a server for execution.

C. Output Page Communication
The editor and output page should communicate without requiring a server.

Use browser-supported techniques such as:
- window.postMessage()
- BroadcastChannel
- In-memory application state where applicable.
- Temporary browser storage where necessary.
Prefer transferring the project directly to the output page using a safe message protocol.

The receiving page should validate the message and handle missing or invalid data gracefully.

Do not execute code received from arbitrary origins.

Important: If the output page is opened in a separate tab, the application must explicitly transfer the current project to that tab. A normal JavaScript variable cannot automatically be shared between two independent pages.

If the output page is refreshed, provide a way to rerun the last transferred code when that project is still available in memory or temporary browser storage.

7. Temporary Files and Privacy
The application must not require a server or database.

All code should be processed locally in the browser wherever possible.

Implement the following rules:
1. Keep project files in browser memory by default.
2. Do not automatically upload source code to a server.
3. Do not require user registration.
4. Do not require an API key.
5. Do not automatically save code permanently.
6. Provide a manual download option.
7. Provide a Clear Project button.
8. Clear the active project when the editor session is closed, according to the chosen session-management design.
Session Management
Use in-memory project storage as the default.

If temporary storage is needed to transfer code between pages, use sessionStorage or an equivalent temporary mechanism.

Do not use localStorage or IndexedDB for automatic permanent project saving.

The user should be able to close the editor and start a new session without the previous project's code being restored automatically.

However, make the behavior clear:
- Closing a separate output tab should not necessarily erase the editor's project.
- Closing the editor tab should end that editing session.
- Refreshing a page may clear in-memory data unless temporary session recovery is explicitly implemented.
- Browser session-storage behavior can vary depending on how tabs are opened and duplicated.
Provide a Clear Project button that immediately removes all project files from the active session.

Ask for confirmation before clearing the project.

10. Code Safety and Isolation
Because users can execute arbitrary JavaScript and HTML, security must be considered.

Implement the following protections:
- Run HTML and JavaScript previews in a sandboxed iframe.
- Do not allow preview code to access the editor's internal DOM.
- Validate messages exchanged between the editor and output page.
- Do not execute code from arbitrary external messages.
- Avoid granting unnecessary iframe permissions.
- Provide execution timeouts where practical.
- Avoid allowing preview code to navigate or control the main editor page.
- Display a warning before allowing external scripts to be loaded.
For Python, use the browser-based runtime and avoid giving programs unrestricted access to application state.

Remember that a sandboxed iframe is not a complete defense against every possible browser security issue. Choose sandbox permissions carefully and test the resulting configuration.

If users can load external libraries or resources, explain that those resources may be downloaded from third-party servers.

⚙️ Important Implementation Decisions
Before building this website, there are three technical points worth getting right.
1. HTML, CSS, JavaScript, and Python need different execution methods
Language	Execution method	Works on GitHub Pages?
HTML	Browser rendering	Yes
CSS	Browser rendering	Yes
JavaScript	Browser JavaScript engine	Yes
Python	Pyodide or another browser-based Python runtime	Yes, with limitations


GitHub Pages hosts static files. It does not execute Python on a server.

Pyodide solves this by bringing a Python runtime into the browser. It is suitable for many educational programs and scripts.
2. The second page needs access to the current code
Suppose a user writes code in index.html and clicks Open Output in New Page.

The application must transfer the current project to output.html.

The recommended approach is:
1. The editor collects the current contents of all project files.
2. It opens the output page.
3. The editor transfers the project using postMessage().
4. The output page validates the message.
5. The output page renders the project inside a sandboxed iframe.
This avoids needing a database or backend.

For reliable communication, the application should also handle cases where the output page loads before the editor is ready to send its code.
3. Closing the website should clear the project
Your requirement is that the code should not remain permanently saved.

The simplest implementation is to keep the project in JavaScript memory and offer a manual download option.

When the editor tab closes, its in-memory project is discarded.

If the application needs to transfer code to another page, it can use temporary session storage or direct messaging. It should not automatically save the project to permanent browser storage.

One important distinction: This clears the application's working copy. It cannot erase copies the user deliberately downloaded, browser history, or data independently retained by third-party resources.
⭐ My Recommendation
For your use case, I recommend building the website as a lightweight online IDE with two pages and four supported file types, rather than attempting to create a complete replacement for VS Code.

Start with these core features:
1. Multi-file editor: Create and edit .html, .css, .js, and .py files.
2. Run button: Execute the selected code.
3. Live preview: Display the webpage on the same page.
4. Separate output page: Open the result in a new tab.
5. Connected files: Automatically load referenced CSS and JavaScript files.
6. Python runner: Execute Python using Pyodide.
7. Temporary workspace: Keep source code in memory without automatic permanent saving.
8. Download project: Export individual files or the complete project as a ZIP.
9. GitHub Pages compatibility: Host the website without maintaining a server.
This gives you a useful, free-to-host coding playground while keeping the architecture relatively simple.

One final consideration: If you eventually want to run unrestricted Python programs, install arbitrary Python packages, or execute C++, Java, or other compiled languages, you will need a different execution architecture. Those capabilities cannot all be provided securely by a static GitHub Pages website alone.
